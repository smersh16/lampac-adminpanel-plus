# Вкладка «Проверка»

Проверяет провайдеры Lampac с сервера, на котором он запущен, и собирает список доменов для маршрутизации через VPN. Запускается только по кнопке, настройки сервера не меняет.

## Как работает проверка

Для каждого тестового тайтла (фильм, сериал, аниме) панель берёт список провайдеров у `lite/events` и прогоняет цепочку:

1. **search**: запрос к провайдеру на localhost самого Lampac (тем же кодом, что и воспроизведение). Если ответ содержит список (`method: link`), спускается по первому элементу (до 5 шагов, шаг `browse`).
2. **link**: запрос `method: call`, получение ссылки на видео.
3. **manifest**: HLS (master → первый вариант), DASH или файл.
4. **segment**: первые 2 КБ первого сегмента.

Провайдер считается рабочим, если прошёл хотя бы один тайтл. Ссылки вида `/proxy/...` раскрываются, чтобы показать реальный узел CDN; `via proxy` означает, что поток тянет сервер Lampac, `via direct` означает, что плеер ходит на CDN напрямую.

Правила запросов:

- Запросы к самому Lampac идут на localhost; к CDN напрямую (`via direct`) идут от процесса Lampac с заголовками, которые провайдер вернул вместе со ссылкой, и браузерным `User-Agent`, если провайдер свой не задал (часть CDN без него отвечает HTTP 500).
- Прямые видеофайлы (`.mp4`, `.m4v`, `.mkv`, `.webm`, `.mov`, `.avi`) проверяются первыми 2 КБ через `Range`, при HTTP-ошибке запрос повторяется без `Range`. Целиком файл не читается: медленный сервер дал бы ложный «нет ответа».
- Таймауты: подключение 10 с, поиск и шаги `browse`/`link` до 40 с, манифест и сегмент до 25 с.

## Как читать отчёт

### Провайдеры

| Запись | Что значит |
|---|---|
| `HTTP 503: ... ответ провайдера: <слово>` | Слово это имя шага, на котором модуль не получил данные (`catalog`, `search`, `files`, `m3u8`, `playlist`, `fileEncode` и т. п.). Это не текст сайта, смысл смотрите по `Fail("<слово>")` в `Controller.cs` модуля. |
| `HTTP 503` без слова | Модуль вернул пустую ошибку; обычно «тайтла нет в каталоге». |
| `ответ провайдера: {}` | Пустой список результатов (чаще всего у торрентов и поиска). |
| `отказ: ...` | Провайдер ответил осмысленным отказом (например, «для этого релиза нет видеоплеера»). Это не ошибка сети. |
| `не удалось подключиться за 10 с (connect timeout)` | TCP-соединение не установилось за 10 с. |
| `нет ответа за 25 с` | Соединение есть, ответа нет. |

HTTP 503 сам по себе не доказывает блокировку домена: провайдер возвращает его и для «нет тайтла», и для «сайт не ответил».

### Домены

| Поле | Значения |
|---|---|
| роль | `provider` (адрес из настроек), `manifest`, `segment` (узлы CDN из реальных ссылок) |
| `net` | `ok`; `UNREACHABLE` с причиной (`dns`, `timeout`, `refused`, `reset`, `tls`); `частично` (работает только IPv4 или только IPv6); `cert` (соединение есть, сертификат не совпадает, домен доступен); `flaky` (проба упала, а реальный запрос прошёл) |
| `req` | `ok` или `FAIL` для реальных запросов, `not tested` если реальный запрос не делался |
| `ips` | адреса по DNS сервера Lampac |

Фильтр «Недоступны» показывает кандидатов для VPN, «Любые сбои» добавляет домены, которые отвечают, но реальный запрос к ним упал. «Служебный адрес» в причине (`0.0.0.0`, `::`, частные адреса) обычно означает подмену DNS на роутере, а не блокировку сайта.

## Что делать с результатом

1. **Домен `UNREACHABLE` в `net` и `FAIL` в `req`** устойчиво, в нескольких прогонах подряд: проверьте с сервера и из контейнера (команды ниже). Если с сервера домен недоступен, это кандидат для VPN.
2. **`dns` с `0.0.0.0`/`::`**: сравните ответы роутера и публичного DNS, ищите интернет-фильтр на роутере.
3. **`flaky` и разовые connect timeout**: не добавляйте в VPN по одному прогону, повторите проверку.
4. **503 с «ответом провайдера» при доступном домене**: это не сеть. Сначала проверьте другой тайтл и настройки провайдера.
5. Для узлов CDN, имена которых меняются (`*.userplay.live`, `*.cdnsqu.com`, `*.mvapspdmpg.com`, `*.kinescopecdn.net`, `*.solodcdn.com`), добавляйте родительский домен. Правила по домену работают только если сервер резолвит имена через DNS роутера.

### Проверка с сервера

```bash
# DNS: ответ роутера и публичного резолвера
dig +short A example.com @192.168.10.1
dig +short A example.com @1.1.1.1

# TCP до узла (с хоста и из контейнера lampac)
nc -vz -w 8 <ip> 443
docker exec lampac bash -c 'timeout 10 bash -c "echo > /dev/tcp/<домен>/443" && echo ok || echo FAIL'

# что видит контейнер
docker exec lampac getent hosts <домен>

# ответ сервера (корень домена, без заголовков провайдера)
curl -4 -sk -o /dev/null -m 10 -w '%{http_code} connect=%{time_connect}s\n' https://<домен>/
```

Адрес `192.168.10.1` взят для примера: подставьте адрес вашего роутера.

## Тестовые тайтлы

Хранятся в `database/adminpanel/healthcheck.json`. По умолчанию: фильм, сериал и аниме с TMDB id. Для аниме у некоторых провайдеров поиск идёт по IMDb и оригинальному (японскому) названию, поэтому заполняйте `original_title` и `imdb_id`. Можно добавлять свои тайтлы по названию и году; бывают провайдеры только для сериалов или только для аниме, поэтому один успешный тайтл достаточен.

## Известные ограничения

- Проверка выполняется процессом Lampac: на результат влияют DNS и маршрут самого сервера и контейнера.
- «Нет в каталоге» зависит от тайтла: проверка не отличает отсутствие тайтла от сбоя провайдера, если модуль возвращает одинаковую ошибку.
- Ссылки на видео часто временные (токен, привязка к IP), поэтому ручная проверка по ссылке из отчёта может не повториться.
